### Decided shape, if it is ever built

- [ ] **the thin route, not the agentic one** — constrain the reply with `--json-schema`, disable the vendor's own tools with `--tools ""`, replace the prompt with `--system-prompt`, and keep the loop in DSH: one completed vendor turn per DSH step, the same conclusion §7d reached for Codex. The agentic alternative — Claude Code running its own loop with DSH tools arriving over MCP — makes one vendor turn span many DSH steps, which is the class §5 exists for, and puts a second compactor on history DSH treats as authoritative. MCP is held in reserve rather than rejected: unlike `agy` it needs no user-owned setup here (`--mcp-config` is per invocation), so an agentic mode stays cheap to add later;
- [ ] **never pass `--bare`**, and keep a test that fails when the vendor makes it the `-p` default, which its own documentation says will happen. It never reads OAuth credentials or the keychain, so it both breaks subscription authentication and touches the one dimension the terms prohibit restricting;
- [ ] **close the repository-content exposure.** Without `--bare`, a `-p` session runs the hooks in a project's `.claude/settings.json` and connects the servers in its `.mcp.json` in a folder the user never trusted, with no trust dialog and no per-server prompt. A primary route invokes exactly that in the user's own workspace. `--safe-mode` disables customizations while leaving auth, model selection, built-in tools and permissions working, and is the candidate answer pending the probe on whether an explicit `--mcp-config` survives it;
- [ ] **dispose with SIGINT before SIGTERM.** SIGTERM leaves the turn unfinished with exit 143 and no recorded result, and a later resume continues that unfinished turn. Background subagents and workflows also extend process lifetime up to ten minutes of idle by default;
- [ ] **run the five probes in the contract document before writing code**, starting with whether one `--input-format stream-json` child serves several turns. That is the same question that had to be settled for `agy` before its session-lived child was written, and the same order applies: probe the real binary, then design.

### What this route would gain over the other two providers

Recorded because it changes what the step model can promise, not merely how it is spelled: `--session-id` lets DSH mint the session identity rather than receive it; `--no-session-persistence` can leave no durable residue in the user's vendor account, which Codex cannot; `--mcp-config` is per invocation; `system/init.capabilities` is feature detection instead of version comparison; and `system/api_retry.error` publishes a typed failure enum, so diagnostics need not guess at vendor wording the way Antigravity's two-entry recogniser list has to.

## 5. Repository-wide provider invariants

- [ ] provider packages use shared `registerProvider()`;
- [ ] **a vendor turn that spans DSH steps never resumes across a rewritten history.** Both providers park a vendor turn inside a tool call while DSH's own loop executes, so one vendor turn spans several DSH steps — and everything that rewrites DSH history lands in exactly that gap: compaction, the tool-result pruner, repair, a user rewind. The same defect was found in both, months apart in the code and minutes apart in the reading, so it is recorded here as a rule rather than fixed twice and forgotten. A provider whose vendor turn spans DSH steps MUST:
  1. record the history prefix the turn was opened against;
  2. refuse to resume when the current request no longer agrees with that prefix — agreement being a prefix match, and growth being a separate question from agreement;
  3. treat DSH's history as authoritative on recovery, rebuilding or realigning the vendor conversation from it rather than continuing on a guess;
  4. digest a message by **everything the provider actually sends for it**, never by id alone. The rule was written as `[id, role, content]`, and content is the part id-only comparison misses: DSH rewrites a message's content while carrying its id over, which the tool-result pruner does exactly, so an id-only check reports agreement across a rewrite that changed everything the model reads. The basis is now stated as a property rather than a field list, because Antigravity's serializer also sends `source` and both independent reviewers found, each with a probe, that a `source`-only rewrite passed the check while the vendor kept the value it was first told. A field that is on the wire and not in the digest makes the check answer the wrong question. **Codex is unchecked against this reading** and must be: its digest is the same five lines, and whether `source` reaches its vendor at all is the question to answer before changing it.

  Conforming today: `antigravity/src/antigravity-primary.ts` (`agreesWithConversation`, checked before answering a blocked MCP call). **Codex no longer has a vendor turn that spans DSH steps** (§7d, 2026-09-03), so this rule stops applying to it — but the hole it names does not close with the parked path, because the vendor THREAD still spans steps. Codex now carries the digest durably instead: `replayState` v2 holds `prefixLength` and `prefixDigest`, verified in `latestCheckpoint()` before a checkpoint is used, and a mismatch falls back to an older checkpoint or rebuilds. That is strictly wider than the guard it replaces, which only ever covered the parked window; the across-turn path was unchecked and demonstrably leaked, confirmed by test before the change. The digest function is deliberately duplicated rather than shared — see the decision in §3;
- [ ] **a vendor turn that spans DSH steps is still open when its parked call is answered.** The sibling of the rule above, and the same shape: the turn spans steps, so the thing that moves in the gap is the vendor's own state rather than DSH's. A vendor that abandoned the parked call — timed it out, errored it, ended the turn around it — answers from whatever the model was handed in its place, and a provider that simply resolves the call and keeps reading records that answer as an ordinary completion. Silent by construction: no exception, no failed step, one whole turn of reasoning built on a result that never arrived. A provider whose vendor turn spans DSH steps MUST assert the turn is still open at the moment it answers, and fail the step rather than resolve into a finished turn.
  Conforming today: `antigravity/src/antigravity-primary.ts` (`openVendorTurn().settled()`, asserted before `bridge.resolve`). **Codex is out of scope for this rule since 2026-09-03**: it parks nothing, so there is no window in which the vendor can abandon a call, and `ActiveTurnQueue.abandonedCall()` was deleted with the parked path (§7d). The rule stands for any provider that reintroduces a spanning turn; the defect it records below is history, not a live guard.
  **Codex was checked on 2026-09-02, had the defect, and it had ALREADY BEEN HAPPENING IN PRODUCTION** — which is why this is a rule and not a note. It was recorded UNCHECKED for exactly one working session and then probed rather than reasoned about: a fake App Server that abandons its outstanding dynamic tool call and completes the turn around it produced no error at all. DSH stops consuming notifications while its own loop runs the tool, so the vendor's agent message and its `turn/completed` sat buffered, replayed on the continuing step, set `finalOutput`, and the turn yielded an ordinary `finish { kind: "stop" }` — a whole turn built on a result the model never received, recorded as a normal answer. The guard scans the buffered events for a `turn/completed` on this turn (or a fatal, non-retrying `error`) before answering, and throws; the turn is discarded and the next request realigns through `startTurn`. A RETRYING error is deliberately not a turn end, and is tested as such. **Confirmed in the maintainer's own session logs the same day, from a bug report rather than from the code**: across six real `ask_user_question` calls (the upstream tool that blocks until a human answers), two came back with the model's complete reply arriving **29 ms and 230 ms** after DSH delivered the tool result — impossible for a real `gpt-5.6-sol` round trip, so the answer had been produced and buffered by the vendor before the result was ever sent. In one the user typed a custom answer and the model replied to the ORIGINAL question as if nothing had been chosen; the user's text then arrived as a fresh next-turn message, which is how the report reads from the outside: *the turn ends before I choose, and my answer is not counted*. It is not a delay threshold and must not be recorded as one — waits of 28.7 s and 149.2 s completed normally (3.7 s and 15.4 s of real model latency) while 26.7 s and 156.9 s did not. Intermittent, i.e. a race. Note the reach of the original find: the Antigravity defect, the Codex history defect and this one are three instances of one window, found by carrying each fix across rather than by three independent reviews. Codex 93 -> 95 tests;
- [x] **root cause found 2026-09-02, and it is broader than the report that started it: the App Server ABANDONS an outstanding dynamic tool call and finishes the turn without it.** Established from the maintainer's own session log, then bounded by live probes against a real App Server.
  The decisive trace is one turn's steps 36 to 38. Step 36 took the vendor 7.7 s and produced an `edit` call; DSH then spent **476 seconds** executing it, because a human was being asked to approve it. Step 37 completed in **5 ms** and step 38 in **23 ms** — both read from a queue DSH had not been consuming, so during those eight minutes the vendor had already emitted the `ask_user_question` call, the final agent message and `turn/completed`. It asked its question and wrapped up the turn without ever intending to wait for either answer. The second occurrence has the same shape with the ask call itself outstanding for 157 s.

Any slow DSH tool — a human-approved `edit`, a long build, a big test run — sits in the same window, and the failure there is silent in a worse way: the model keeps planning against results it never received.
  Live probes bound the behaviour rather than explain it away. Parking a single tool call for 60 s, 120 s and 180 s against real `codex-cli` on a small conversation, the vendor waited correctly every time and the continuation delivered the marker.   **Checked against the vendor's own documentation, 2026-09-02.** `codex app-server generate-json-schema` and `generate-ts` emit the App Server protocol from the installed binary, which is the closest thing Codex has to a specification.   What the same artifacts DO give is the vendor's own vocabulary for the call's fate, which DSH had been throwing away: a `dynamicToolCall` thread item carries `status: "inProgress" | "completed" | "failed"` alongside `success` and `durationMs`, and `item/completed` for it was being dropped by the event loop with every other non-`agentMessage` item. The healthy ordering is not assumed — in all three live probes that item arrived within 1 ms AFTER DSH's response and never before it. Codex 95 -> 97 tests.
  **A way to make the vendor actually wait — probed and CONFIRMED 2026-09-02.** The protocol says the word "block" exactly once: `isBlocking` on `ToolRequestUserInputParams`, nowhere else, and the client-to-server surface has no keepalive to reset any clock. But the channel that matters was not in the protocol document at all.   **Both follow-up questions probed on the APP SERVER path and answered 2026-09-02, both yes.** A raw JSON-RPC probe drove `codex app-server --stdio` directly against `codex-cli 0.150.0` on `gpt-5.6-sol`:

  **The approval gate is now known exactly, and it is not what was guessed above.** An MCP tool call is gated by `mcpServer/elicitation/request`, carrying `serverName` and `_meta.codex_approval_kind: "mcp_tool_call"`. Two things follow for DSH. Second, the reply is an MCP **elicitation** (`{ action: 'accept' | 'decline', content, _meta }`), not an approval `{ decision }`; answering with the wrong shape reads as a rejection, which cost this probe one whole run before the shape was right. `handleServerRequest` already returns the correct elicitation shape and hardcodes `decline`, so accepting exactly DSH's own bridge server by `serverName` and declining everything else is a small, bounded change. `_meta.persist` offers `["session", "always"]`, which suggests the grant can be persisted rather than prompted per call — not tested.

  **`turn/start.outputSchema` — accepted subset established by probe, 2026-09-02 (P0 #1 of the supplied design, answered).** The field exists and is documented as "Optional JSON Schema used to constrain the final assistant message for this turn". Codex passes it through to `response_format` under the name `codex_output_schema`, so the accepted subset is **OpenAI Structured Outputs strict mode**, and the vendor's rejections name each rule exactly:
  1. the root must be `type: "object"` — a bare `anyOf` at the root is refused (`got 'type: "None"'`);
  2. **`oneOf` is not permitted** (`In context=(), 'oneOf' is not permitted`); `anyOf` is permitted when nested;
  3. **`const` is not permitted** — use an `enum` of one member;
  4. `additionalProperties: false` is required on EVERY object (`'additionalProperties' is required to be supplied and to be false`);
  5. **every property must appear in `required`.** An optional parameter therefore has to be expressed as a nullable union (`type: ["string", "null"]`) and listed as required.
  A working shape was proven end to end: a root object with one `decision` property whose value is a nested `anyOf` of per-variant objects, each carrying an `enum`-of-one discriminator and a typed `arguments` object. The model answered `{"decision":{"kind":"tool_call","name":"read_file","arguments":{"path":"src/main.ts"}}}`, and with a nullable optional it answered `{"path":"src/main.ts","encoding":"utf-8"}`.
  **What this means for the proposed design.** The mechanism works, and the subset is publicly documented rather than vendor-internal — a real advantage over depending on the `features.code_mode` flag. But the design's own §6.2 schema is INVALID on three counts (top-level `oneOf`, `const`, missing `additionalProperties`) on top of its untyped `arguments`, and rule 5 carries a consequence the design does not mention at all: DSH tool schemas have optional parameters, so a rewriter must turn each into a nullable union — and because the model then emits an explicit `null` for anything it omits, the adapter must strip nulls before handing arguments to DSH, or tools receive `encoding: null` where they expected the key to be absent. That is a concrete defect waiting for whoever implements it, and it is also a token and quality cost: every optional field becomes a decision the model must make on every call.

  **Reasoning-continuity A/B — RUN TWICE, THEN REFUTED BY INDEPENDENT VERIFICATION (2026-09-02). Read this before trusting any token figure in this section.** The question was whether one-completed-turn-per-step makes the model re-derive its plan and re-spend reasoning. Something host-side finishes registering in the first ~30 s of an `app-server` process and lands in the prompt: with identical `thread/start` and `turn/start` params and no schema and no tools, a thread started at t=0.26 s measured `inputTokens` 14,433 and one started at t=31.7 s measured 17,968 — and a thread that was the FIRST in a fresh process but started at t=45 s also paid 17,968, so it is elapsed time, not thread order. Corroborated at zero cost: `mcpServerStatus/list` grows over the same window (`codex_apps` gains ~5.0 KB, a new `openai-api-key-local-confirmation` server appears). In every one of the author's probes the "cheap" arm happened to run first in a freshly spawned process.
  Re-measured correctly, cold against cold: **`outputSchema` costs 94 tokens**, not 3,600 — the same 94 measured again warm-against-warm. `dynamicTools` costs **58**. Neither rewrites the vendor prompt measurably. The reported 25,415-token gap is 7 x 3,535 = 24,745 of artifact with a **residual of 670 tokens, 0.65%**; on uncached-input-plus-output the residual is ~248 tokens, about **1.5%**. So the community claim that structured-output schema tokens are effectively free was RIGHT and this section's refutation of it was wrong.

Any future probe here must compare per-request uncached input plus output, or read `total`.

  | B->A | parked | 5,488 | 15,311 | 197 | 0 | **15,508** |

  Three things this establishes. **The warm-up artifact is absent under the production config** — `firstInput` is 5,488 for parked and 5,517 for stepped in BOTH positions, cold and warm alike, confirming the verifier's finding; the 29-token gap between them is the residual declaration asymmetry (`dynamicTools` against `outputSchema`), measured rather than assumed. **Cost tracks POSITION, not arm** — whichever arm runs second in a process pays more (12,902 and 15,508) than whichever runs first (11,204 and 11,154), regardless of which arm it is. **The least-confounded comparison, first position against first position, is 11,204 against 11,154 — 0.4%.** Averaged across positions stepped is nominally cheaper (12,028 against 13,356), but the within-arm spread from position reaches 4,304 tokens and swamps any between-arm effect.
  Quality is identical and now replicated four times: six probes and the correct answer in every arm. One earlier claim also fails to replicate — "parked emits no reasoning items" held at 0 in one run but 126 in the other, so that is unstable too. A new unexplained effect is recorded rather than theorised: the second arm in a process accumulates more UNCACHED input across its requests while its first-request input is identical, which looks like prefix-cache interference between threads but was not investigated.
  **So the cost objection to one-completed-turn-per-step is gone entirely, not merely reduced.** Combined with `dynamicTools` being outside the published contract while `outputSchema` is inside it, the documented design and the cheaper design are now the same design. That is a reason to revisit the deferral, not to act on it today.

  **The honest state of the question: the parked-versus-stepped token difference is UNDETERMINED, and it is certainly not 25%.** A counterbalanced A/B was not run. What survives from the original runs is only what was counted as events rather than summed as tokens: arm B emits one `reasoning` item per turn where arm A emits none, and both arms solved the task correctly in six probes, replicated. So step-by-step does reason afresh per turn, but the official reasoning guide states GPT-5.6 defaults to rendering available reasoning from earlier turns (`all_turns`), which is why that costs 174-314 tokens rather than a full re-derivation.

Meanwhile `outputSchema` IS in the published contract and **`dynamicTools` is NOT** — see the entry below. The documented mechanism is the stepped one.

This inverts how the choice was framed earlier in this section: the path this suite ships rests on an undocumented field, while the proposed stepped design rests on a documented one.

  **The bridge was answering MCP incompletely, found 2026-09-02 by questioning the setup rather than the vendor.** Codex puts a **`progressToken` in `_meta` of every `tools/call`** — captured verbatim from the wire, alongside `callId`, `threadId` and an `x-codex-turn-metadata` block.   C is the one that settles it. `instructions` suppresses what the model SAYS on each cycle but does not change how often it is asked; the progress notifications are what cut the cycles themselves, roughly in half. Both are worth having and they act on different costs — instructions on output tokens per cycle, progress on the number of billed requests. All three runs completed correctly with the marker delivered, so neither lever risks the result.
  **Consequence for shipped code:** the Antigravity bridge should answer `progressToken` too, but whether `agy` sends one has NOT been checked — do that before implementing, rather than assuming the two vendors agree.

  **What the cadence actually is, read off the probe log 2026-09-02:** across the 200 s block the vendor emitted seven `thread/tokenUsage/updated` + `account/rateLimits/updated` pairs — 40.7 s, 73.9 s, 106.8 s, 140.2 s, 173.9 s, 207.0 s — each a completed, BILLED model request, most of them a full `reasoning` -> `agentMessage` turn and one (140.2 s) billing with no visible output at all. This is not display noise: a blocked tool call costs real turns against the user's quota and rate limits roughly every 33 s.
  **Hypothesis that fits every observation in this section, and is NOT established:** the vendor polls an in-flight tool call and hands the model a turn each cycle to decide whether to keep waiting. It explains the fixed cadence, the billing, the content of the model's replies ("I'll keep waiting without restarting it") — and, crucially, the abandonment itself: a dynamic tool call is not dropped by a timeout but by the model DECIDING to stop on one of these cycles, which is exactly why it is intermittent and worsens with context size rather than firing at a fixed number of seconds. Confirming it needs the outbound request payload, which the App Server does not expose; do not record it as fact until someone has it.
  **One lever we do control, from the official reference:** "Codex reads the MCP instructions field returned during initialization and uses it as server-wide guidance alongside the server's tools." A bridge server supplies that field, so it can tell the model how to behave while a call is outstanding. That may cut what each cycle GENERATES; nothing suggests it stops the cycles happening. Untested.
  One confound is unresolved and cheap to settle: the probe prompt said "wait for it however long it takes", which may itself have invited the narration; a bridge would never phrase it that way. Worth one run with a neutral prompt before the cadence is recorded as unavoidable.
  The guard above is the whole remedy DSH can offer: it cannot make the vendor wait, so it refuses the turn instead of recording an answer built on a result the model never got. ## 7a. Codex thread handling — decision taken and implemented

Measured against real `codex-cli 0.150.0`; the numbers and the protocol facts are in `ARCHITECTURE.md` under *Codex vendor threads*.

The former fork-per-turn design got **zero** prompt-cache credit on every turn, while resuming one thread gets cache credit for ~90% of input, and a partial `thread/rollback` does not disturb it. Forking also left one persisted vendor thread per DSH message in the user's own vendor account, each carrying that turn's runtime context and project contract.

- [x] decide whether to replace fork-per-turn with `thread/resume` plus `thread/rollback` for divergence, and implement it (`perf(codex)!: resume the vendor thread instead of forking every turn`). An ordinary turn resumes; `thread/rollback` realigns when DSH's history has diverged from the vendor thread's tip; `thread/fork` is kept only for a checkpoint that is neither the tip nor an ancestor of it. This keeps the cache, keeps exact-turn semantics, and leaves one vendor thread per session instead of one per message. Codex 61 -> 69 tests; `verify:local` and live acceptance (primary + full 15-scenario suite) pass;
- [x] record the reason for the chosen thread strategy in the code — the shared start/fork/resume configuration and the resume/rollback/fork decision are now commented at the call site in `packages/codex/src/codex-plugin-dsh/adapter.ts`;
- [x] decide whether this suite should clean up the vendor threads it creates (`thread/delete` / `thread/archive` exist). Decided: no. Deletion touches data in the user's vendor account and the maintainer has said old sessions do not matter, so no cleanup is implemented and none is planned against previously created threads. Threads created before this change (one per message, under the old fork-per-turn design) still exist in the user's vendor account exactly as they were;
- [x] **`thread/inject_items` reaches the model — verified** (`pnpm test:live:inject-items`). It had always succeeded while being invisible through both `thread/read` and `thread/resume`, so its effect was unknown, and the adapter depends on it for every message that follows a checkpoint. The probe shapes one request so a value can only have arrived by injection: `prepareCodexHistory` splits at the last run of user-authored messages, and a tool-result message is not user-authored, so a history ending `tool-result(SECRET), user(question)` puts the secret in the injected half and the question in the input half with no overlap. Both halves are asserted rather than trusted — the suite sniffs the JSON-RPC written to the vendor and checks the secret is in the one `inject_items` frame and absent from the one `turn/start` frame — and only then reads the answer, which was exactly the secret. No checkpoint is needed for the probe, which is why it costs one turn.

Note on cost framing: the measurements are token counts the vendor reports. ChatGPT/Codex subscription limits are message-weighted rather than token-metered, so a large cached-token saving does not automatically translate into the same saving on the user's `5h`/`Weekly` counters. Do not promise that it does.

## 7d. Codex stepped-turn transport — IMPLEMENTED AND LIVE-ACCEPTED 2026-09-03

**Decision.** Move `nishi-dsh-codex` from the parked `item/tool/call` design to **one completed vendor turn per DSH step**, with the model answering as a structured decision under `turn/start.outputSchema`. Decided by the maintainer on 2026-09-02 on the evidence in §5. Implementation deliberately left to a fresh session rather than bolted onto the day that produced the evidence. This supersedes the "leave the tree as it is" note in §5 for the stepped design; the MCP-bridge idea is not deferred but **obsolete**, since the stepped design removes the problem the bridge was meant to work around.

**Implemented 2026-09-03** across five commits: the schema module and its inverse, the durable checkpoint contract, the stepped turn loop, auxiliary-request isolation, and the removal of the parked path. Codex 97 -> 145 tests. **Every live suite was re-run against the new transport and passes** — `primary` 1/1, `acceptance` 9/9 covering all 15 scenarios, `inject-items` 1/1, `tool-result-continuation` 1/1, `web-search` 1/1, `web-search-routed` 1/1 — because a suite not re-run after the transport changed is not evidence for the tree that changed. The first `primary` run FAILED, and that failure is recorded in `docs/verification/README.md` and in the last item of the list below. What the design brief below got wrong, and what only measurement settled, is recorded in *What the implementation changed about the plan* at the end of this section — read that before trusting any earlier paragraph here.

**Why, in the order the reasons actually carry weight.**
1. **`outputSchema` is in the published contract and `dynamicTools` is not.** Verified independently against `codex app-server generate-json-schema` and `generate-ts` from the installed 0.150.0: `ThreadStartParams` carries no `dynamicTools` field in the v2 schema or the TS bindings, and `DynamicToolSpec` is defined but unreferenced. The binary honours it, so the mechanism is real — but the path this suite ships today rests on an undocumented field, and the stepped design does not.
2. **The cost objection is gone.** A counterbalanced run with the production isolation config put the least-confounded comparison at 11,204 against 11,154 uncached-input-plus-output — 0.4%, with position noise larger than any arm effect. The earlier "23-25% premium" was a process warm-up artifact plus a summing error; both are recorded in §5.
3. **A whole class of failure disappears by construction.** No open vendor turn while DSH executes a tool means nothing to abandon, no yield boundary at which the model can decide to stop waiting, no `wait(..., terminate: true)`, and no idle billed requests. That is the defect that started this investigation — `ask_user_question` answered before the human chose — removed structurally rather than caught by a guard, and it removes any need for the undocumented `direct_only_tool_namespaces` key.
4. Quality parity is replicated four times: identical probe counts and correct answers in every arm.

**The working schema shape, measured rather than designed.** `outputSchema` reaches `response_format` as `codex_output_schema` in OpenAI Structured Outputs strict mode. Five rules, each named by the vendor's own rejection message: the root must be `type: "object"`; `oneOf` is refused while nested `anyOf` is accepted; `const` is refused, so use an `enum` of one member; `additionalProperties: false` is required on every object; every property must appear in `required`. This shape was proven end to end, twice:

```
{ type: "object",
  properties: { decision: { anyOf: [ <per-tool variant>, <final variant> ] } },
  required: ["decision"], additionalProperties: false }
```

each variant being an object with an `enum`-of-one `kind`, an `enum`-of-one `name`, and a typed `arguments` object. **Do not ship the schema from the design document that prompted this**: it breaks three of the five rules and leaves `arguments` untyped, which is exactly what makes a call missing every required field schema-valid.

**Known pitfalls, to be handled rather than rediscovered.**
- **Optional tool parameters.** Rule 5 forbids optional properties, so each must become a nullable union (`type: ["string", "null"]`) and be listed in `required`. The model then emits an explicit `null` for whatever it omits, so **the adapter must strip nulls before handing arguments to `ToolsService`** — otherwise a tool receives `encoding: null` where it expected the key to be absent. The nullable form is measured working; the null-stripping is not written.
- **Call ids.** Codex mints its own today (`call_...`, `exec-...`), unique per call. Under this design the model authors them, so DSH must mint and map its own.
- **Tool results into history.** Use `thread/inject_items`, which is live-verified on Codex (`test:live:inject-items`). The design document's prose `<tool_output>` fallback is strictly worse and should not be used.
- **Auxiliary calls.** Codex does not use `purpose`-carrying requests today, so no carve-out is needed — but a forced schema must never be applied to one if that changes.
- **Keep the abandonment guard until the parked path is actually gone.** `ActiveTurnQueue.abandonedCall()` becomes unreachable once nothing is parked; delete it with the parked path, not before.

**What the implementation changed about the plan (2026-09-03).** Written after the fact, because several paragraphs above were wrong and the record is worth more than the tidiness.

- **"Codex does not use `purpose`-carrying requests today, so no carve-out is needed" was the worst line in this brief.** It described an inability to distinguish, not a discriminator: the adapter read `options.purpose` nowhere. `compaction-basic/src/summarizer.ts:145-162` sends `tools`, `maxTokens` and `purpose: 'compaction'` through `ctx.llm` under the ordinary session id, replaying a *prefix* of the conversation with its replay states intact — so `latestCheckpoint()` found a checkpoint behind the live tip and the adapter took the **destructive `thread/rollback` branch**, cutting real turns out of the live conversation. Confirmed by executable test. What prevented it in practice was the blanket `maxTokens` rejection this brief also proposed to relax, so fixing that alone would have opened the hole. `session-title-llm/src/index.ts:258-259` additionally races the primary request on the same session id, which the concurrency guard refused. Auxiliary requests now ignore checkpoints, use an `ephemeral: true` thread, emit no replay state, carry a registry key distinct from the session id, and are outside the guard.
- **They send no `outputSchema` at all**, rather than the message-only schema Antigravity needs. Under this transport the tools exist *only* in that schema and the vendor's own are off via `isolationConfig()`, so omitting it suppresses tool use by construction and leaves the summarizer its plain-text contract. Both independent reviewers reached that conclusion separately.
- **The optional-parameter alarm was real and then dissolved.** Probes 1 and 5 showed the model inventing values for optionals it was not asked about — a fabricated `timeoutMs: 10000` for `bash`. Round 2 called it a release blocker forced by strict mode. It is not: probe 8 (three encodings, three runs each) and probe 9 (the *byte-identical* 56-variant catalog, only the prompt changed) give **twelve runs with nulls and zero inventions** once the request says to leave defaults alone. The mitigation is one sentence in `CODEX_APP_SERVER_DEVELOPER_INSTRUCTIONS`, and a test fails if it is removed. The earlier probes had simply never told the model.
- **The full production catalog is accepted**: 56 variants, **352** object properties, 39,367 bytes, nesting depth 5. Round 2 raised strict mode's documented property and size ceilings as a possible blocker; they do not bind here. One data point only — no search for the actual limit.
- **`historyDigests` was not deleted, it moved.** The brief treated the parked-window guard as something the stepped design makes unnecessary. The vendor *turn* stops spanning DSH steps, but the vendor *thread* does not, and the across-turn path never checked transcript content at all: rewriting a message's content while keeping its id left the vendor holding the old text while DSH recorded the answer against the new. Confirmed by test before the change. The digest is now durable, in `replayState` v2 as `prefixLength` + `prefixDigest`, verified before a checkpoint is used — one rolling hash, not the per-message array, which would grow replay metadata quadratically.
- **A tool-call turn must persist replay state**, which the brief never says. The parked branch yielded `finish(tool-calls)` with none because the vendor turn was still open; under stepping it is not, and a tool-call response without a checkpoint makes `latestCheckpoint()` skip it, so every result step resumes an older checkpoint or rebuilds and the prompt cache dies silently.
- **`prepareCodexHistory` needs a lookback.** With the checkpoint on the assistant message that made the calls, `messages.slice(checkpoint.index + 1)` excludes it, so only the results would be injected. Measured: the vendor **accepts** an orphan `function_call_output`, logs `Orphan function call output`, and **silently ignores it** — the turn completes normally and the model never sees the result. The synthetic `function_call` is re-emitted ahead of each output, and `decisionDigest` pins the blocks it is rebuilt from.
- **Tool results stay a paired `function_call` + `function_call_output`.** A three-arm live test (paired, user-role message, orphan) settled it: paired and user-role are behaviourally indistinguishable — 6/6, marker used, no duplicate call — so the choice fell to design. The pair leaves the rebuild path untouched and keeps the boundary between a tool's output and a user's words.
- **`dynamicTools` in `codexOutputSchema` is absent for an empty catalog, and that turn is unconstrained.** Live acceptance caught what 560 unit tests did not: a primary request with no tools sends no schema, the model correctly answers in prose, and the decision parse — gated on "is this auxiliary" rather than "did we send a schema" — failed the turn with `response is not valid JSON`. The gate is now the schema, recorded on the turn where it is built.
- **Streaming of the final answer is gone**, and that is a product regression accepted deliberately. Under a forced schema the answer arrives as raw JSON (28 deltas of `{"`, `decision`, `":{"`). Both reviewers judged a correct incremental JSON string extractor — split escapes, surrogate pairs, duplicate keys where `JSON.parse` takes the last value a scanner already emitted first, and deltas that cannot be retracted — not worth its risk. Commentary still streams as reasoning.
- **One process per DSH step, measured rather than assumed**: 286 ms median of four runs, spread 10 ms (spawn+initialize 137, `config/read` 33, `skills/list` 43, `thread/start` 71). Retaining the connection would save ~213 ms per step. A live probe confirmed repeated `thread/resume` on one connection works, so retention is *possible*; both reviewers judged it not worth the dispatcher, poison-state rules and idle eviction it needs, and the measurement is recorded so the question can be reopened with a number rather than a feeling. That figure does not capture any TLS/HTTP2 setup the first model request pays upstream.

**What this does NOT settle.** The magnitude of any residual cost difference — only "not 25%" is established. Whether the vendor's reasoning-across-turns default (`all_turns`, per the official reasoning guide) holds up under a forced schema at production context size; it was measured cheap on a small task only. The unexplained position effect in uncached accumulation. And `features.code_mode: false`, which the adapter sets today, is a measured no-op on the yield path — still open wherever the parked path survives.

**Sequencing.** This is a transport change on a provider that is thawed and waiting on independent validation and a freeze. It should land as its own change with its own live acceptance, and the freeze evidence must be re-taken afterwards.
