# The `agy` published contract, and what this suite depends on

Written 2026-09-02, after reading the vendor's own documentation end to end rather than reasoning from probe history. It exists because this package has more than once depended on behaviour the vendor never published — the shape of the risk is known from `packages/codex`, where the shipped adapter turned out to rest on an undocumented `dynamicTools` field (`ROADMAP.md` §5, §7d).

This file is a **contract inventory**, not a design document. Every row says where a dependency stands with the vendor: published, ambiguous, observed-only, or not a CLI surface at all. The architecture argument built on it lives in `ROADMAP.md` §3.

## What the vendor actually publishes

Recorded because most of it was never written down here, and several dependencies previously carried as probe findings turn out to be contract.

**Headless transport** (`/docs/cli/headless/`). `--input-format stream-json` "maintains a persistent conversation across multiple turns within a single process", requires `--output-format stream-json`, and takes one JSON object per line on stdin whose documented shape is exactly:

```json
{ "event": "user", "message": { "content": "..." } }
```

Only `text` content blocks are supported in streamed messages. Each turn emits its own `result`. Events are `init`, `step_update` (`step_type` of `user_input`, `agent_response`, `tool`), and `result`. The result envelope carries `conversation_id`, `status`, `response`, `duration_seconds`, `num_turns`, `usage`, `structured_output`, `json_schema` and an optional `error`. `status` is one of `SUCCESS`, `ERROR`, `CANCELED`, `INTERRUPTED`, `INVALID`, `WAITING`, `RUNNING`. **`num_turns`, `usage` and `duration_seconds` accumulate across the session** — the adapter's usage subtraction is therefore contract-mandated, not a workaround. Closing stdin exits `0`. A tool needing approval is **soft-denied**: the run continues and exits `0` with a stderr notice. Slash commands do not work inside a streaming session.

**Permissions** (`/docs/cli/permissions/`). Rules live in `~/.gemini/antigravity-cli/settings.json` under `permissions.allow` / `deny` / `ask`, precedence **Deny > Ask > Allow**. Syntax by class: `read_file(path)`, `write_file(path)`, `read_url(host)`, `execute_url(host)`, `command(prefix|regex)`, `unsandboxed(prefix)`, `mcp(server/tool)`, `mcp(server/*)`. Workspace files are allowed by default for read/write; anything unconfigured defaults to Ask. The CLI's own headless denial message names this same file and key.

**MCP** (`/docs/cli/mcp/`). Global `~/.gemini/config/mcp_config.json`, workspace `.agents/mcp_config.json`. One `mcpServers` map; per server `command`/`args`/`env`/`cwd` or `serverUrl`/`headers`, plus `authProviderType`, `oauth`, `disabled` and **`disabledTools`** — a published per-server tool denylist.

**Agent definitions** (`/docs/subagents#custom-subagents`). Workspace agents at `.agents/agents/<name>.md` or `.agents/agents/<name>/agent.md`, global at `~/.gemini/config/agents/`. Published frontmatter keys: `name`, `description`, `tools` (string[], default `[]`, "explicit list of tools permitted"), `mainAgent` (bool, default true), `subagent` (bool, default true), `model` (`inherit`/`flash`/`pro`), `commandExecutionPolicy` (`off`/`auto`/`eager`/`sandbox`, default `sandbox`), `mcpServers`, `skills`, `plugins`. Tool names appearing anywhere in the docs: `view_file`, `replace_file_content`, `grep_search`, `run_command`, `invoke_subagent`, `call_mcp_tool` (only as permission syntax).

**Sandbox** (`/docs/cli/sandbox/`). `nsjail` on Linux, `sandbox-exec` on macOS, `AppContainer` on Windows; confines agent-executed terminal commands. Setting `enableTerminalSandbox`, default false.

**Status line** (`/docs/cli/statusline/`). A `statusLine` command in `settings.json` receives a state JSON on **stdin** carrying `session_id`, `conversation_id`, `transcript_path`, `model`, `context_window` (`total_input_tokens`, `total_output_tokens`, `context_window_size`, `used_percentage`, `current_usage` with a cache breakdown), **`quota`** (per model id: `remaining_fraction`, `reset_time`, `reset_in_seconds`), `plan_tier`, `email`, `execution_mode`, `sandbox`, `vcs`. This is the only published machine-readable quota channel in the product; `/docs/cli/credits/` documents no non-interactive way to read quota at all.

## Findings from this pass

**1. `structured_output` goes STALE, and the shipped `schema` transport consumes it silently.** Probed twice on 1.1.24 in one streaming process with one `--json-schema`:

- three neutral turns (capitals of France/Japan/Peru) each produced a fresh, correct `structured_output`. Per-turn enforcement is real, which is what the tree recorded against 1.1.22;
- but a turn whose user instruction competed with the schema ("reply with exactly the word banana and nothing else") answered in **prose** — `response` was `"banana\n"` with no JSON in it — and the envelope's `structured_output` still held **the previous turn's object**, `{"kind":"message","text":"apple"}`, verbatim.

`structuredResult()` (`schema-transport.ts:277`) trusts `structured_output` first and has no freshness test, so that turn is read as a valid decision the model never made. Where the stale object is a `tool_calls`, DSH re-executes the identical call — a mechanically exact generator of repeated identical tool calls, and one that survives every fix made on 2026-08-31. This is the first mechanism of that class found in the transport itself rather than in the envelope, the ids or the model's discipline.

**Reproduced, and the remedy demonstrated end to end** (`agy 1.1.24`, `gemini-3.7-flash-low`, two runs, one process each):

| Run | Schema | Turn 1 | Turn 2 |
|---|---|---|---|
| S1 | `{kind,text}` | `response` carries the JSON; `structured_output = {"kind":"message","text":"The capital of France is Paris."}` | `response = "banana\n"`, no JSON anywhere in it; `structured_output` **identical to turn 1's**, verbatim |
| S2 | same plus a required `turn_nonce` | envelope declared `N7-AAA`, reply carried `turn_nonce:"N7-AAA"` | envelope declared `N7-BBB`, `response = "banana\n"`; the stale `structured_output` still carries **`N7-AAA`** |

So the remedy stays inside published surface and is measured, not designed: put a per-turn nonce in the forced schema, set it in the envelope, require it in the reply, and fail the turn when it does not match. S2 shows the stale reply is then distinguishable from a fresh one by construction. It also gives the ambiguity in row 10 a safe reading — treat per-turn enforcement as best-effort and detect its absence, rather than resting on it.

A second, cheaper check falls out of the same data and should be used alongside rather than instead: on both stale turns the turn's own `response` contained no JSON at all, so requiring the decision to appear in this turn's `response` catches the same failure without touching the schema.

**2. Two permission stores exist, the binary honours BOTH, and we read only the undocumented one.** The documented location is `~/.gemini/antigravity-cli/settings.json` → `permissions.allow`, and the CLI's own headless denial message names exactly that: *"Add an allow-rule under permissions.allow in settings.json"*. This package instead reads `~/.gemini/config/config.json` → `userSettings.globalPermissionGrants.allow`, and its fresh-install error text instructs the user to add `mcp(dshtools/*)` there. Both files exist here: `settings.json` held only `trustedWorkspaces`, while `config.json`'s `userSettings` held `globalPermissionGrants`, `enableTerminalSandbox`, `autoExecutionPolicy`, `nonWorkspaceFileAccessPolicy`, `artifactReviewMode` — semantically the documented settings under different names.

Probed on 1.1.24 with one grant, `command(echo)`, and a prompt that runs `echo MARKER-PW4412`, each arm a separate process, both stores restored byte-identical afterwards (sha256 verified):

| Arm | Grant in | Outcome |
|---|---|---|
| baseline | neither | `run_command` **ERROR**, `permission check failed ... user denied permission`, `jetski: no output produced` on stderr |
| 1 | `settings.json` → `permissions.allow` (documented) | **executed**, marker returned |
| 2 | `config.json` → `userSettings.globalPermissionGrants.allow` (ours) | **executed**, marker returned |

So this is not a broken dependency — it is a redundant one bound to the undocumented half. The fix is small and worth making anyway: read the documented store as well, and make the error text name the documented file the way the vendor's own message does, since that is the file a user following the vendor's documentation will edit.

**3. `disabledTools` is a published isolation lever we do not use.** A per-server tool denylist in the MCP config is contract, where the agent `tools:` allowlist is documented for subagents and probe-known **not** to gate MCP tools at all (row 16). Anywhere isolation currently rests on the allowlist, part of it can rest on a published key instead.

**4. Workspace-scoped MCP registration loads the server and hides its tools — so `mcp-bridge`'s two-step user-owned setup is unavoidable.** `.agents/mcp_config.json` is published as a supported scope, which would have removed `mcp-bridge`'s once-per-machine global registration, its largest deployment cost. Probed with a trivial stdio MCP server declared there, `--add-dir` on that directory, and the model asked for its tool:

- the vendor **did** load and connect it: it wrote a schema cache at `~/.gemini/antigravity-cli/mcp/probews/probe_marker.json` on every such run, which only a completed `tools/list` produces;
- the model was **not** given it. Asked to enumerate its own declarations with filesystem access forbidden — and with the cache directory deleted first, so it could not read the answer off disk — it named only `dshtools`, the globally registered server, and reported `probews` as unavailable;
- one earlier run *appeared* to succeed and did not: the model located the cached schema file with `view_file`, guessed the call, and `call_mcp_tool` dispatched it by name as far as the permission gate (`permission check failed for mcp "probews/probe_marker"`). Dispatch by name works for a configured server; declaration is what the model lacks. Reading that run as "injection works" would have been the wrong conclusion, and it is why the enumeration control was added;
- a control in the same workspace confirms `.agents/` itself is read: an agent defined at `.agents/agents/probeagent.md` resolved under `--agent` and its instruction token came back in the reply.

This **confirms** the record in `ROADMAP.md` §3 rather than superseding it — that probe used `.agents/plugins/<name>/mcp_config.json` and reached the same place by another door.

**Probe D, the follow-up worth having: the grant cannot move into the workspace either.** With both global stores restored to their originals, a `permissions.allow` block written to `.agents/settings.json` in the workspace was ignored — the same `command(echo)` that arms 1 and 2 executed came back `permission check failed`. That run doubles as the baseline for finding 2. So `mcp-bridge` requires two things from user-owned global configuration, `agy mcp add` and a grant, and neither can be shipped inside our own ephemeral workspace. That is now established rather than assumed.

**5. The only published machine-readable quota channel is the status-line payload.** It carries per-model `quota.remaining_fraction`, `reset_time`, `reset_in_seconds` plus the full context-window breakdown, delivered on stdin to a user-configured command — but it is a TUI feature and does not fire in a headless turn, so it cannot replace row 22 as it stands. What it does settle is that the vendor publishes no non-interactive quota API at all: the usage capability is not an undocumented shortcut past a documented path, it is a capability the CLI contract does not offer. That makes row 22 an explicitly accepted internal dependency rather than an oversight — and it is the one dependency in this file whose name a vendor rename would break. **Corrected by finding 8:** siblings exist (`businessaicode.v1beta`/`v1main` `FetchQuotaStatus`), so the fallback is not absent — it is remote and account-authenticated, which puts it outside this package's credential boundary rather than outside the vendor's API.

**6. The prefix cache still engages on 1.1.24 under the production config — row 20 holds, and the earlier zeros were the threshold, not a regression.** The first probes reported `cache_read_tokens: 0` at 30k, 45k and 61k *cumulative* input, which looked like the 20418-of-23496 figure recorded on 1.1.22 had stopped reproducing. It had not: those runs used the **default** agent, whose own prefix is ~15k per turn — below the engagement threshold — and the tree's own Codex work established that an under-configured probe measures the probe.

Re-measured with the shipping shape — ephemeral workspace, `.agents/agents/dsh-primary.md` with `tools: [finish]` and `inheritCustomizations: false`, `--add-dir`, `--agent`, `--sandbox`, the real `bridge-output.schema.json` under `--json-schema`, one `full` envelope of 142k characters (system prompt, 44-tool catalog, 20 history messages) followed by two small `delta` envelopes in the same child:

| Turn | Envelope | Cumulative `input_tokens` | Own uncached input | Own `cache_read_tokens` |
|---|---|---|---|---|
| 1 | `full` | 30,596 | 30,596 | 0 |
| 2 | `delta` | 32,908 | **2,312** | **28,613** |
| 3 | `delta` | 35,548 | **2,640** | **28,596** |

93% of a ~30.6k prefix served from cache on every continuation, and a continuation costs ~2.4k of new input against the ~30.6k a fresh conversation pays — the same ratio the 1.1.22 figure recorded, on a larger prefix. The session-lived child's justification stands on the installed binary.

Two contract details fell out of it, both worth having written down:

- **`input_tokens` accumulates UNCACHED input, and `cache_read_tokens` accumulates separately.** Turn 2 re-sent the whole ~30k context yet the cumulative figure rose by only 2,312. So the adapter's subtraction yields that turn's own uncached input, which is the right thing to report — but nothing in the envelope is a per-turn total, and a reader who assumes `input_tokens` is "everything the model saw" will under-count by whatever the cache served;
- **`init.tools` reported 57 tools with `tools: [finish]` in force**, reconfirming row 16 on 1.1.24: that field is the vendor's registry, not the agent's allowlist, and must never be read as an isolation check.

**7. There is no quota subcommand, and the vendor publishes none — settled by enumeration, not inference.** `agy --help` on 1.1.24 lists every subcommand it has: `agent`/`agents`, `changelog`, `help`, `install`, `mcp`, `mic-serve`, `models`, `plugin`/`plugins`, `update`. No `quota`, no `usage`, no `credits`. The vendor documents `/credits` and `/usage` (`/docs/cli/credits/`, `/docs/cli/commands/usage/`) as interactive TUI panels and describes no non-interactive query. Finding 5 already established that the status-line payload is the only published machine-readable channel and that it does not fire headless; this closes the remaining question by enumerating the surface rather than reasoning about it. Row 22 is therefore the only door, and it is the same door every other tool uses: `RetrieveUserQuotaSummary` appears verbatim in the 1.1.24 binary as `/exa.language_server_pb.LanguageServerService/RetrieveUserQuotaSummary`, and both `CLIProxyAPI` and `CodexBar` document reading it. Third-party claims of a "dedicated quota command" for this vendor mean the TUI slash command or this RPC; there is no third thing. Finding 12 measures what opening that door costs: no turn, and no token.

**8. Row 22 does have a sibling, and the "no fallback" line in finding 5 was too strong.** The 1.1.24 binary also carries a non-`v1internal` quota surface: `/google.cloud.businessaicode.v1beta.PredictionService/FetchQuotaStatus`, its `v1main` twin, and the REST form `/{$api_version}/{parent=projects/*/locations/*}:fetchQuotaStatus`, against `cloudcode-pa.googleapis.com`. So the name `RetrieveUserQuotaSummary` is not a single point of failure in the way finding 5 asserted — there are two publicly-namespaced siblings. What remains true, and is the actual reason it is not a fallback for this package: they are remote and account-authenticated, so reaching them means holding the user's credential, which this package does not do and will not do. Record it as "a fallback exists but lies outside the credential boundary", not as "no fallback exists".

**9. The vendor trims its own trajectory, which the divergence check cannot see.** The binary carries `Trajectory has exceeded max length, clearing %d steps starting from %d`. `sentDigests` is one-directional by construction: it detects DSH rewriting history behind a conversation the vendor has already heard, and it cannot detect the vendor dropping steps from the front of its own trajectory. After such a drop the vendor holds a different prefix than the one we delivered, every subsequent `delta` extends a conversation only we believe in, and nothing in the current design reports it. Silent by construction, and it should worsen with session length — precisely where the session-lived child earns its keep. **PROBED TWICE, 2026-09-03, and it does not fire in any regime this route can reach.** Both runs used the production shape -- sterile workspace, `dsh-primary` with `tools: [finish]`, `--add-dir`, `--sandbox`, the forced schema -- one live child, `gemini-3.7-flash-low`, with `--log-file` read afterwards.

- **81 turns, 242 vendor steps, context ~21.5k.** One `conversation_id` and one vendor `trajectory_id` throughout, all 81 `SUCCESS`, zero occurrences of the message. A codeword planted in turn 1 came back verbatim in turn 81.
- **9 turns each carrying ~70 KB of inert filler, context ~239k.** Same result: one conversation, 9/9 `SUCCESS`, zero occurrences, and the turn-1 codeword returned verbatim after ~239k of intervening context. The cached portion grew monotonically to 233k and never fell.

The second run also settles something bigger by accident: the route survives a context ABOVE the `contextWindowTokens` this package advertises (`200_000`), so DSH's own compaction fires long before the vendor's budget on this evidence, and the vendor would have to be trimming *below* DSH's compaction threshold for this to bite.

**What the probes do NOT establish.** The mechanism exists -- the string is in the 1.1.24 binary -- and its limit is **`max_trajectory_tokens`**, a protobuf field with a getter (`GetMaxTrajectoryTokens`), which means it is **server-configured and not a client constant**: it is absent from the `init` event, absent from the log, unreadable from the binary, and changeable without a client update. So this is a bounded negative, not an absence. A lower tier, another model, or a server-side change could put the budget under a reachable size.

**The detection signal, if it ever does fire, needs neither the log nor the binary.** Dropping the front of the trajectory must collapse the cached portion of the very next request while nothing on our side rebuilt. That is visible in the `usage` this adapter already reads: a fall in `cache_read_tokens` mid-conversation with no rebuild is the symptom, and both probes confirm the healthy shape it would break -- monotonic growth, 0 -> 233k across nine turns and 0 -> 455k across eighty-one.

Related strings in the same build, recorded because a later reader will look for them: `Failed to fork current conversation: %v. Starting fresh conversation.`, `forking is not supported for conversations that have invoked subagents`, `StopStreamingConversation: Flushed %d steps from drip to conversation`.

**10. Slash commands are intercepted client-side in print mode.** The binary carries `pass --disable-slash-commands to send /%s to the model as literal text`, and the flag's own help says it disables "slash command and skill expansion in print mode". So by default a leading `/command` in print mode is handled by the CLI and does not reach the model. That makes `agy -p "/usage"` a candidate for a published, zero-token quota read — the docs say the command opens a panel, so it may print nothing useful headless, but the cost of finding out is one run and possibly no tokens. **Probed 2026-09-04, and it is better than the candidate suggested: see finding 17.** Two consequences either way: this package's own envelopes always begin with a JSON object rather than a slash, so nothing we send is at risk today; and any future feature that forwards user text verbatim as the first character of a turn must pass `--disable-slash-commands` or a user prompt beginning with `/` will be eaten by the CLI.

**11. What `agy` is, since it explains the shape of everything above.** A 209 MB Go ELF whose internal product name is `jetski` (`/google/bin/releases/jetski-devs/...`, which is also the source of the `jetski: no output produced` line this repository already knows). It is built on the Codeium/Windsurf stack: `exa.language_server_pb.LanguageServerService`, `exa.extension_server_pb`, `exa.codeium_common_pb`, `X-Codeium-Csrf-Token`, `cascade`/`CASCADE_*` feature flags, `SUPERCOMPLETE_*`. Remote surfaces are `cloudcode-pa.googleapis.com` with `google.cloud.businessaicode.v1beta`/`v1main` plus internal `JetskiService`. This is why quota lives on a loopback language server instead of in the CLI: `agy` is a CLI front end over that language server, not a self-contained client. It also explains `extension_server_port` and `extension_server_csrf_token` as protobuf fields — they address the desktop app's server, not this CLI's, which is why the harvest against our own child needs no token at all.

**12. The quota listener comes up before stdin, so a harvest needs no turn -- probed, and it costs nothing but a cold start.** Finding 5 established that no published channel serves quota headless and finding 7 closed the enumeration, leaving row 22 as the only door; what stayed unmeasured was the price of opening it, since the narrowing to this package's own child recorded quota as unavailable until a turn had run. Two arms on `agy 1.1.24` from a scratch directory outside this repository, neither writing a single byte to stdin: **A** minimal, `--input-format stream-json --output-format stream-json` alone, and **B** the production shape, adding `--add-dir`, `--json-schema`, `--sandbox`, `--model gemini-3.7-flash-low` and `--print-timeout 600s`. Listeners were located the way `usage-source.ts` locates them -- descendant pids from `/proc/<pid>/task/<pid>/children`, then `/proc/<pid>/fd` -> `socket:[inode]` -> `/proc/net/tcp{,6}` with `st=0A` -- and read with the shipped request: `POST /exa.language_server_pb.LanguageServerService/RetrieveUserQuotaSummary`, `Content-Type` and `Connect-Protocol-Version: 1` as the only headers, `ANTIGRAVITY_METADATA_BODY` as the body, no token.

Both arms behaved identically: **two loopback listeners on the `agy` pid itself at +510 ms**, before any turn could exist, and the real 1570-byte payload -- the same two groups and four buckets the live suite records, `remainingFraction` and `resetTime` per bucket. `--sandbox` does not remove the listener. Nothing was billed, and the evidence for that is negative on every channel a turn would touch: zero stdout lines, zero `result` events, zero stderr bytes, no `init` event, and no file created in the vendor's `conversations/`.

Three details the harvest design must carry, none of which follow from the endpoint merely existing:

- **Auth is not ready when the port is.** The first ~2 s answer `HTTP 500 {"code":"internal","message":"internal: failed to get load code assist response: error getting token source: You are not logged into Antigravity."}`, and the 200 arrives at +2223 ms (arm A) / +2212 ms (arm B). Production never meets this, because it harvests against a child whose turn already warmed the token. A harvest-only child must poll until 200 -- and must not report that 500 as "not logged in", which is exactly what it claims to be.
- **The two ports are not interchangeable.** One speaks HTTPS only -- plain HTTP returns `400 Client sent an HTTP request to an HTTPS server` -- and the other HTTP only, failing `EPROTO` under TLS. So `tryFetch()`'s loop over `['http','https']` per listener is load-bearing rather than defensive, and collapsing it to a single scheme would break half the cases on this build.
- **Zero tokens is not zero residue.** `SIGKILL` on the production-shaped arm left an empty crash log in the user's `~/.gemini/antigravity-cli/crashes/`, a directory that was empty before it. A throwaway harvest child must therefore be disposed through the ordinary grace path, or every quota read writes the user a crash that never happened. And any run at all, harvest-only included, writes the ordinary vendor state: `cache/onboarding.json`, `updater/update_status.json`, `log/cli-*.log`, one `implicit/*.pb`.

What the probe does **not** establish is that the reading is true: the same external survey that produced this recipe also recorded a reading reporting headroom while generation returned 429 (`CLIProxyAPI` issue 1015). Cheap and turn-free is not the same as authoritative.

**13. Nothing this route can do produces `CANCELED` or `INTERRUPTED`; both ways to cut a turn short report `ERROR`.** The seven published statuses were being collapsed into `status === 'SUCCESS'`, and before typing them it was worth knowing which of the six are actually reachable. Probed on 1.1.25, one child per arm, a long generation deliberately interrupted:

- **`--print-timeout` expiry** (arm A, `8s`, while the model was mid-essay): `result` with `status: "ERROR"`, `error: "timeout waiting for response"`, `response: ""`. The child stays alive for about a second and then exits `1` when the next input line is written -- so the conversation is gone, not merely interrupted.
- **`SIGINT` to the child** (arm B, 6 s into the turn): the identical envelope -- `ERROR`, `timeout waiting for response` -- 168 ms after the signal, and the child exits `1` twelve milliseconds later.

Two consequences, and the first is not a hypothetical: **`--print-timeout` is on the production invocation**, set from `turnTimeoutMs`, so arm A *is* the production turn-timeout path. It reports `ERROR` and leaves the conversation unusable, which is exactly what the adapter already does with it (abandon and fail). No change was needed there, and that is the finding.

The second is why the statuses were typed anyway. A status this client cannot provoke is precisely the kind the vendor can begin sending without a client update -- the same argument as `max_trajectory_tokens` in finding 9 -- and two of the six are not failures at all (`CANCELED`, `INTERRUPTED`) while two more mean the turn has **not settled** (`WAITING`, `RUNNING`), which is the opposite of the completed failure a single non-success bucket reports. The classification therefore ships with the cancellation branch **unreachable and correct** rather than reachable and wrong, and a cancellation now reports DSH's documented `ABORTED`, which `dsh-llm` turns into a terminal `{ kind: 'aborted' }` instead of `{ kind: 'error' }`.

**14. A cold quota read returns the same figure as a turn-harvested one; what varies is the RPC's content, not the temperature of the child.** Finding 12 established that the listener exists before stdin. The question left open was the one that decides whether a turn-free read may ship: is the answer TRUE, or a placeholder the vendor serves while its own upstream fetch is still failing? Probed on 1.1.25 through this package's own `createHostPlatformDiscovery()` and `AntigravityQuotaHarvestCache` rather than hand-rolled HTTP, so the evidence is about the shipped path:

- **timings, from a scratch directory with nothing written to stdin:** two listeners on the child's own pid at **+261 ms** (`--sandbox`: +255 ms), and the real payload -- the same two groups and four buckets the live suite records -- at **+1.8 s**, after ~1.5 s of the harvest's own retrying. Zero bytes on stdout while the reading is taken, no `init`, no `result`, **no file in the vendor's `conversations/`**, and disposal through the grace path (end stdin, terminate, wait) leaves `crashes/` **empty** where finding 12's `SIGKILL` left a crash log;
- **cold equals warm.** The live suite now runs both against one account minutes apart: the turn-harvested read and the turnless read both reported **`usedPercent = 1.03`** on the Gemini weekly bucket, the cold one in 2.2 s;
- **the content is the flaky part, and it is not a cold/warm distinction.** Within one hour the Gemini weekly bucket read 43.89% used (reset `2026-09-06T23:41Z`), then 0% used (reset `2026-09-10T18:35Z`) -- a window ROLL, visible in the reset moving, not a placeholder -- and for a stretch after a `500 failed to get load code assist response` every bucket came back with **no `remaining` field at all**: at the first 200, at 5 s, at 15 s, at 30 s, and **after a completed `SUCCESS` turn on the same child**. A turn does not fix it, so there is no warm reading to prefer.

That last state is safe only because of a line that now has to stay: `parseRetrieveUserQuotaSummary` (`usage-source.ts:172`) skips a bucket whose fraction is not a finite number in `[0,1]` and throws when none survive, so an empty payload surfaces as an honest `UNAVAILABLE` rather than as invented headroom. Removing that skip would turn a vendor hiccup into a confident "quota is full".

What none of this establishes is that the number is true when it exists: the survey behind finding 12 recorded a reading reporting headroom while generation returned 429 (`CLIProxyAPI` issue 1015). Turn-free, bounded and agreeing with itself is not the same as authoritative.

**15. `agy --version` prints the bare version and nothing else, and it is the only published way to learn the build.** `1.1.25`, one line, exit 0. The `init` event carries no version (only `agent`, `cwd`, `json_schema`, `model`, `permission_mode`, `tools`), the result envelope carries none, and the vendor's own `updater/update_status.json` holds only `{"success":true,"message":"Already on the latest version."}` -- so a separate process is the cost of knowing, or the build is not known. The argument for paying it arrived during this pass without being asked for: **the installed binary moved 1.1.24 to 1.1.25 between the audit and these probes.** A crash report that does not name its build is a report about a binary nobody can identify afterwards. The read is therefore fire-and-forget, once per adapter, and only a version-shaped token from the output is kept.

**16. `--json-schema` is a parse of the model's own text, not a constraint on it -- which is why a turn can carry no decision at all, and why asking again works.** Finding 1 established that `structured_output` goes stale; what it did not establish is *why* a turn produces none of its own, and that is what decides whether anything can be done about it. Probed on 1.1.25, one child per arm, from a scratch directory:

- **The block is written by the model, into its own answer.** A turn's `response` reads `The capital of France is Paris.\n{"kind":"completed","text":"The capital of France is Paris.","toolAction":"Finishing task","toolSummary":"Task completion"}` -- prose, then the JSON, in one text field. `structured_output` came back `{"kind":"completed","text":"The capital of France is Paris."}`: the model's own `toolAction` and `toolSummary`, which the schema does not declare, were **filtered off**. A constrained decoder cannot emit a field it was not given and then drop it; a post-hoc parse-and-filter is exactly what that looks like. So the schema is a request plus an extractor, and a turn where the model writes only prose leaves the extractor nothing -- reported `SUCCESS`, with the previous turn's object still in the field.
- **A fenced block defeats the vendor's own extractor.** Asked to restate an answer as JSON, the model returned ```` ```json\n{\n  "kind": "RETRY",\n  "text": "banana"\n}\n``` ```` in `response` -- correct, complete, and stamped as asked -- and `structured_output` **stayed stale**. The payload was plainly there and the vendor did not take it. This is the case `structuredResult`'s fall-through to `response` was written for on a hunch; it is now measured, and `responseRow` reads it because it scans to the first `{` rather than requiring the whole field to parse.
- **The conversation is healthy afterwards.** Three turns in one child -- fresh block, prose-only (stale), then a third turn -- all `SUCCESS`, exit 0 on stdin close. Nothing about a turn that carried no decision damages the child, which is the premise the repair turn rests on.
- **The model restates on request, and restates the same thing.** With the shipping agent definition in force and the bridge schema bound, a `repair` envelope naming the lost turn brought back the identical decision under the new stamp: a `tool_calls` reply came back with the same call, the same `call_read_file_001` id and the same arguments; a `message` reply came back with the same text (`toolSummary: "Repairing message response"`). Two arms, both first try.
- **What did NOT reproduce.** Upstream reports large minified-JSON prompts returning empty `SUCCESS` with zero usage, the internal pubsub having killed a slow subscriber (`google-antigravity/antigravity-cli#840`, open against 1.1.15/1.1.16). Retried on 1.1.25 at 120 KB and 300 KB of minified JSON: both `SUCCESS` with a fresh block, 58.7k and 76.7k input tokens. It is not the mechanism behind the production failure on this build, and the earlier 108 KB arm that "passed" proved nothing either way -- it carried prose inside JSON, which is the arm that issue reports as passing.

**Where this sits with the vendor.** Nobody has reported the stale-field case: `#794` (open) is the same family with the field *absent* under `--print --json-schema`, which is strictly easier to detect than a field holding a schema-valid object from an earlier turn. `#902` (open, 1.1.22) reports long tool-using turns in `stream-json` ending `CANCELED` or `SUCCESS` with an empty response, an incomplete 1.1.18 fix -- worth noting against finding 13, which concluded `CANCELED` was unreachable from this client: it is reachable from somewhere, so the `cancelled` branch stays typed. `#848` (open, 1.1.17) reports `status ERROR` with `context canceled` after a valid completion, which is where this package's recognizer for that wording comes from -- quoted from a report rather than measured here, and marked as such in `vendor-stderr.ts`. `#813` (open) reports `--sandbox` diverting headless structured-output runs onto the CLI's own guide files; `--sandbox` is on the production invocation, so it was probed on 2026-09-04 rather than left as a worry. **This route is not exposed, and the reason is structural.** Two arms on 1.1.25 differing only in the flag, both in the shipping shape -- `--agent dsh-primary` with its `finish`-only allowlist, the bridge schema bound, a workspace holding three real files and a prompt demanding they be read: both returned the identical DSH `tool_calls` decision naming exactly the three requested paths, with **zero native tool steps** in either. There is nothing for the vendor to divert the model onto, because the agent definition leaves it no file tool; its only route to a file is a DSH tool call, and DSH decides what that reads. The reporter's own arm -- the default agent, which does carry native file tools -- was NOT reproduced here: it needs `--dangerously-skip-permissions` to get past headless denial, and that tests the vendor's defect rather than this package's exposure to it.

**17. `agy -p "/usage"` serves the whole quota, machine-readable, for zero tokens -- and it is a PUBLISHED channel, unlike the one this package uses.** Finding 10 left this unprobed and finding 5 had concluded no published channel serves quota headless. Both are now wrong in the same direction. Probed on 1.1.25:

- `agy -p "/usage"` prints one tab-separated record per bucket and exits `0`.
- `agy -p "/usage" --output-format json` returns `status: SUCCESS`, `conversation_id: ""`, `num_turns: 0` and **every usage counter at zero**, with the payload under a `command` key: `{name: "usage", data: {description, groups: [{name, description, buckets: [{id, name, description, window, remaining_fraction, reset_time}]}]}}`. Four buckets across two groups, `remaining_fraction` at full float precision, `window` as `"weekly"` / `"5h"`.
- It creates no conversation: the vendor's `conversations/` directory held 1395 entries before and after.

That payload is what `usage.ts` projects -- bucket id, window label, kind, remaining fraction, reset time -- with no field missing and no derivation needed. The consequence is larger than the finding: **`usage-source.ts`, `quota-cold-harvest.ts` and `quota-harvest-cache.ts` are ~800 lines whose entire job is to reach the same numbers over a private interface** -- descendant pids from `/proc`, socket inodes matched against `/proc/net/tcp`, an unauthenticated loopback POST to `exa.language_server_pb.LanguageServerService/RetrieveUserQuotaSummary`, and a PID-scoped trust boundary invented to make that safe. Rows 22 and its neighbours are the observed-only dependencies with the worst standing in this whole inventory, and they exist because finding 5 concluded there was no published alternative. There is one, it costs a subprocess and no tokens, and it answers cold. Replacing the source is not done here and is not a freeze-time change; it is recorded as consequence 8.

## Probe hygiene

Every probe above ran from a scratch directory outside this repository on `gemini-3.7-flash-low`, against `agy 1.1.24` up to finding 12 and `agy 1.1.25` for findings 13 to 16 -- the binary self-updated mid-pass, which is finding 15's own argument. The cache probe of finding 6 mutated nothing at all — its workspace, agent definition and schema file were disposable copies. `agy mcp add` was never called, so the vendor's MCP registry still holds only `dshtools`. The two global config files were backed up first, mutated one arm at a time, and restored byte-identical — `sha256sum` verified against the backups after the last arm. The `~/.gemini/antigravity-cli/mcp/probews/` schema cache the vendor wrote during probe 4 was deleted afterwards. The listener probe of finding 12 wrote nothing to stdin, created no conversation, and touched no configuration; the one artefact it left that the vendor would not have written by itself was the empty crash log its `SIGKILL` produced, which was removed -- `crashes/` is empty again. No `agy` process survived either arm. These probes are exploratory and are not retained as a suite; the recipes are in this file.

## Consequences

1. **LANDED.** Row 10 was the load-bearing ambiguity of the `schema` transport and finding 1 made it a live defect. Every envelope now carries a `turn` stamp the reply must echo, a decision stamped for another turn is refused as `ANTIGRAVITY_STALE_DECISION`, and a refused turn abandoned the conversation instead of continuing it. Bridge protocol `v2` -> `v3`. **What a refused turn does next has changed twice since**: it keeps the healthy child (2026-09-04, `rc3-review.md`), and then asks it to say the turn again rather than losing the step (consequence 7 below). Antigravity 133 -> 138 tests; `test:live:primary` 8/8, `test:live:session-continuation` 1/1, `test:live:mcp-bridge` 1/1 and `test:live:agent-allowlist` 1/1 against real `agy 1.1.24`, which is the first live evidence on that build.
2. **LANDED, THEN DELETED WITH ITS CALLER.** Row 21 was redundant rather than broken (finding 2), and both stores were made readable with the documented one named first in the setup text. One commit later the `mcp-bridge` removal deleted the precondition that was the only caller, and the two-store reader with it. The finding stands and is worth keeping written down -- the vendor honours both stores, and only one of them is documented -- but this package no longer reads either, because nothing it ships needs a vendor permission grant.
3. **ACTED ON — the transport is gone.** Rows 16, 18, 19 and 23 were what `mcp-bridge` rested on, all observed-only, and row 18 had already broken in production. Findings 4 and D added that its setup cost was irreducible: two pieces of user-owned global configuration, neither shippable in our workspace. Rows 1-9 — everything the `schema` transport needs besides row 10 — are published, and it needs no setup at all. `mcp-bridge` was removed outright on 2026-09-03 with the `transport` key; `ROADMAP.md` section 3 carries the decision, including the two blocking holes independent review added to this argument. Rows 18, 19, 23 and 24 now describe no shipping code, and row 16 survives as the standing reason `init.tools` must never be read as an isolation check. Same direction as Codex's §7d stepped-turn decision, for the same reason.
4. The published event and envelope names (rows 1-5) deserve a test that asserts them against a recorded live sample, so a vendor rename fails a test instead of a session.
5. **DONE.** `verification/README.md` no longer implies the audited vendor is `1.1.22`: all seven live suites carry `1.1.25` evidence, re-run on 2026-09-03 and again on 2026-09-04 after the tree changed under them.
6. Row 20 is settled on 1.1.24 (finding 6): the cache engages under the shipping config, so the session-lived child stays. What is still open is narrower — the exact engagement threshold, which this probe brackets between ~15k (default agent, no credit) and ~30k (production shape, 93% credit) without locating.
8. **LANDED, and it was the largest simplification this inventory ever pointed at.** Finding 17's channel replaced the private RPC on 2026-09-04. `AntigravityUsageCommandSource` runs `agy -p "/usage" --output-format json` and projects `groups -> buckets` directly; `usage-source.ts`, `quota-cold-harvest.ts` and `quota-harvest-cache.ts` are deleted (~800 lines), and with them the `/proc` descendant walk, the socket-inode matching against `/proc/net/tcp`, the unauthenticated loopback POST and the PID-scoped trust boundary that existed only to make that defensible. Row 22 is retired rather than defended. Three things came with it rather than being lost: the vendor's own group name now reaches the display, where the old path had to strip cadence words off a label and would have rendered `gemini-weekly` as "gemini"; the adapter no longer takes a quota cache at all, so a turn child is no longer inspected for anything; and the skip-on-missing-fraction discipline is kept verbatim, because inventing headroom from an absent field is the one failure a quota display must not have. The two prerequisites this entry named were answered: latency is a ~3.2 s median against the old cold path's ~2.2 s, which buys the deletion and is bounded by a 60 s floor on spawning plus single-flight; the rate-limited-account question could NOT be answered -- the account under test sits at 96-99% remaining and cannot be exhausted to order -- so it is carried as the one open unknown, and the failure mode if it answers badly is an honest `UNAVAILABLE`, not a wrong number.

7. **LANDED.** Finding 16 turned finding 1's detection into a remedy. A stale stamp no longer loses the step: the adapter asks the same live conversation to say that turn again, in a `repair` envelope carrying no DSH history, once and never twice. Bridge protocol `v3` -> `v4`. The `turn-timeout` recognizer landed with it, because finding 13's `timeout waiting for response` is the production timeout wording and had been reporting as `unrecognized` since it was measured.
